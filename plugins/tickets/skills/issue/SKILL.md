# Issue の書き方

正本は [fracturelabdev/.github の CONTRIBUTING](https://github.com/fracturelabdev/.github/blob/main/.github/CONTRIBUTING.md) と、同じ場所の Issue Forms。この skill は開かなくても書けるようにまとめた案内で、食い違いがあれば CONTRIBUTING を優先する。

## 型とラベル

型はタイトル接頭辞で決める。次の 4 つのみ。

| 接頭辞 | ラベル |
|---|---|
| `[Bug]` | `bug` |
| `[改修]` | `improvement` |
| `[作業]` | `task` |
| `[アイデア]` | `idea` |

ラベルが対象リポジトリに無ければ先に作る。存在しないラベルは GitHub が黙って付けない。

## タイトル

`[タイプ] 対象 + 何が/どうなる` の形で 40 字以内。原因の推測はタイトルに書かない。

## 型ごとの必須欄

- `[Bug]`: 発生環境 / 再現手順 / 期待する動作 / 実際の動作 / 完了条件。対象外は推奨
- `[改修]`: 背景 / 現状の課題、変更内容、完了条件。対象外は推奨
- `[作業]`: 作業内容、完了条件（成果物があれば場所を書く）
- `[アイデア]`: 背景 / 困りごと、提案。PR は紐付けない。着手するときは `[改修]` を起票し直す

## 書き方

- 完了条件はチェックボックスで、第三者が確認できる状態にする。「修正する」だけは不可
- 対象外は空にしないことを推奨する。この Issue の外側を定義するもの。後続の Issue があれば番号を書く
- 本文は日本語。変更内容は 3 点以内、作業内容は 5 点以内が目安。超えるなら Issue を分割する

## 起票

本文をファイルに書き、`gh issue create --title "..." --label improvement --body-file body.md` で渡す。シェル展開で本文を渡さない（バッククォートや `$` が壊れる）。

個人のフックや判定スクリプトの実行は前提にしない。
