# Issue の書き方

正本は [fracturelabdev/.github の CONTRIBUTING](https://github.com/fracturelabdev/.github/blob/main/.github/CONTRIBUTING.md) と、同じ場所の Issue Forms。この skill は開かなくても書けるようにまとめた案内で、食い違いがあれば CONTRIBUTING を優先する。

## 型とラベル

型はタイトル接頭辞で決める。次の 4 つのみ。ラベル名は、CONTRIBUTING が起票に使う Issue Form に書かれているものと 1 対 1 にする。

| 接頭辞 | ラベル | PR の紐付け |
|---|---|---|
| `[Bug]` | `bug` | あり |
| `[改修]` | `improvement` | あり |
| `[作業]` | `task` | 任意 |
| `[アイデア]` | `idea` | なし。着手するときは `[改修]` を起票し直す |

## タイトル

`[タイプ] 対象 + 何が/どうなる` の形で 40 字以内。原因の推測はタイトルに書かない。

## 型ごとの必須欄

完了条件はどの型でも必須。チェックボックスで、第三者が確認できる状態にする。「修正する」だけは不可。対象外には、この Issue で扱わないことを書く。後続 Issue があれば番号を書く。Form が対象外を任意にしていても空にしない。`[アイデア]` の Form には完了条件と対象外の欄が無く、`[作業]` の Form には対象外の欄が無い。その項目は本文に同じ見出しで足す。

- `[Bug]`: 発生環境、再現手順、期待する動作 / 実際の動作、完了条件、対象外
- `[改修]`: 背景 / 現状の課題（300 字以内）、変更内容（3 点以内）、完了条件、対象外
- `[作業]`: 作業内容（5 点以内）、完了条件（成果物があれば場所を書く）、対象外
- `[アイデア]`: 背景 / 困りごと（300 字以内）、提案、完了条件、対象外。PR は紐付けない

Form の任意欄（改修の関連 Issue / PR、作業の期限、アイデアの期待効果 / 懸念）は空でよい。

## 書き方

- 本文は日本語。背景・課題は 300 字以内
- 箇条書きは原則 3 点以内。5 点を超えるなら Issue を分ける
- 空白 Issue は作成できない。上の必須欄を欠かさない

## 起票

作成先のリポジトリを先に 1 つ決め、ラベルの確認、不足ラベルの作成、起票をすべてそのリポジトリだけで行う。作成先が決まらないときは何も作らない。

1. 作成先の指定があればその `OWNER/REPO` を使う。無ければ `gh repo view --json nameWithOwner --jq .nameWithOwner` の結果を使う。コマンドが失敗する、結果が空、または意図したリポジトリと違うときは中止する
2. `gh label list --repo OWNER/REPO --limit 200 --json name --jq '.[].name'` でラベル名を取る。既定の 30 件では足りないので `--limit 200` を付ける。200 件を超えるときは増やす。型のラベルと完全一致するものが無いときだけ、同じ `--repo` で `gh label create <label> --repo OWNER/REPO` を実行する
3. 必須欄を見出しにした本文をファイルに書く。シェル展開で本文を渡さない（バッククォートや `$` が壊れる）
4. `gh issue create --repo OWNER/REPO --title "[Bug] ..." --label bug --body-file body.md` を実行する。`--label` は、手順 2 のあと作成先にある型のラベルにする（`[改修]` は `improvement`、`[作業]` は `task`、`[アイデア]` は `idea`）

`gh issue create --label` は、作成先に無いラベルだと失敗する。ラベルを外して起票したり、別リポジトリのラベルで代用したりしない。

個人のフックや判定スクリプトの実行は前提にしない。
