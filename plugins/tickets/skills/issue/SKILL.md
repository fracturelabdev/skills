# Issue の書き方

正本は [fracturelabdev/.github の CONTRIBUTING](https://github.com/fracturelabdev/.github/blob/main/.github/CONTRIBUTING.md) と、同じ場所の Issue Forms。この skill は開かなくても書けるようにまとめた案内で、食い違いがあれば CONTRIBUTING を優先する。

## 型とラベル

型はタイトル接頭辞で決める。次の 4 つのみ。ラベル名は、CONTRIBUTING が起票に使う Issue Form に書かれているものと 1 対 1 にする。

| 接頭辞 | ラベル | PR の紐付け |
|---|---|---|
| `[Bug]` | `bug` | あり |
| `[改修]` | `improvement` | あり |
| `[作業]` | `task` | 任意 |
| `[アイデア]` | `idea` | なし。着手するときは `[改修]` を起票し直す |

## タイトル

`[タイプ] 対象 + 何が/どうなる` の形で 40 字以内。原因の推測はタイトルに書かない。

## 型ごとの必須欄

完了条件はどの型でも必須。チェックボックスで、第三者が確認できる状態にする。「修正する」だけは不可。対象外には、この Issue で扱わないことを書く。後続 Issue があれば番号を書く。

Form の `validations.required` が付くのは、Bug の発生環境・再現手順・期待する動作 / 実際の動作・完了条件、改修の背景 / 現状の課題・変更内容・完了条件、作業の作業内容・完了条件、アイデアの背景 / 困りごと・提案だけである。対象外は Bug と改修では任意、作業とアイデアには欄が無い。完了条件はアイデアの Form に欄が無い。CONTRIBUTING は完了条件を必須とし、対象外への明記を求めている。食い違うときは CONTRIBUTING を優先する。Form が対象外を任意にしていても空にしない。欄の無い完了条件と対象外は、本文に同じ見出しで足す。

- `[Bug]`: 発生環境、再現手順（5 手順以内。6 手順以上は分ける。4 手順と 5 手順は分けない）、期待する動作 / 実際の動作、完了条件、対象外
- `[改修]`: 背景 / 現状の課題（300 字以内）、変更内容（3 点以内。4 点と 5 点も分ける）、完了条件、対象外
- `[作業]`: 作業内容（5 点以内。4 点と 5 点は分けない。6 点以上は分ける）、完了条件（成果物があれば場所を書く）、対象外
- `[アイデア]`: 背景 / 困りごと（300 字以内）、提案、完了条件、対象外。PR は紐付けない

Form の任意欄（改修の関連 Issue / PR、作業の期限、アイデアの期待効果 / 懸念）は空でよい。

## 書き方

- 本文は日本語。背景・課題は 300 字以内
- 点数の書いていない箇条書きは、原則 3 点以内。4 点と 5 点は原則から外れるが、ここでは分けない。6 点以上（5 点を超える）なら Issue を分ける
- 欄に点数が書いてあるときは、その点数が上限であり、直前の分け方より優先する。`[改修]` の変更内容は 3 点が上限なので 4 点と 5 点も分ける。`[作業]` の作業内容は 5 点が上限なので 4 点と 5 点は分けず、6 点以上で分ける。`[Bug]` の再現手順は 5 手順が上限で、6 手順以上なら分ける
- 空白 Issue は作成できない。上の必須欄を欠かさない

## 起票

作成先のリポジトリを先に 1 つ決め、ラベルの確認、不足ラベルの作成、起票をすべてそのリポジトリだけで行う。作成先が決まらないときは何も作らない。

1. 作成先の指定があればその `OWNER/REPO` を使う。無ければ `gh repo view --json nameWithOwner --jq .nameWithOwner` の結果を使う。コマンドが失敗する、結果が空、または意図したリポジトリと違うときは中止する
2. ラベル名は次で全部取る。`gh label list --limit` は既定 30 件で、数を指定してもその件数で打ち切る。打ち切っても終了コードは 0 のままなので使わない

   ```
   gh api --paginate "repos/OWNER/REPO/labels" --jq '.[].name'
   ```

   `--paginate` は次のページが無くなるまで取る。各ページはラベルの配列で、`--jq` はそのページごとに評価される。`.[].name` はページ内の名前をすべて出すので、ページごとの出力を続けたものが全件になる。全ページを 1 つの JSON 配列に包むとき以外、`--slurp` は要らない。終了コードが 0 でないときは中止する。終了コードが 0 なら、名前が 0 件でも取得成功として手順 3 へ進む
3. 正規名は Issue Form の `labels` と 1 対 1 である。`1-bug.yml` は `bug`、`2-improvement.yml` は `improvement`、`3-task.yml` は `task`、`4-idea.yml` は `idea`。GitHub のラベル名は大文字小文字を区別しない。正規名と、手順 2 の各 `name` を、大文字小文字を無視した完全一致で照合する（`bug` は `bugfix` に一致しない）。一致した既存の `name` を、表記を変えずに `LABEL` にする。`Bug` があるときに `bug` は作らない。一致が 2 件以上なら中止する
4. 一致が 0 件のときだけ、同じリポジトリで `gh label create <正規名> --repo OWNER/REPO` を実行し、その正規名を `LABEL` にする。`gh label create` の必須引数はラベル名だけである。`--description` と `--color` は任意で、色を省くと無作為な色になる。`--repo` は作成先をこのリポジトリに固定するために付ける。`--force` は付けない（既存ラベルの色と説明を上書きする）。終了コードが 0 でなければ中止する。名前を変えて作り直さない
5. 本文は作業ツリーに書かない。相対パス `body.md` は、既にある `body.md` を上書きし得る。`BODY=$(mktemp)`、EXIT trap の設定、本文の書き込み、`gh issue create` は、同じシェルプロセスで続ける。別のコマンドや別シェルに分けると、次のシェルの `$BODY` は空で、作ったファイルのパスは渡らない。ファイルは残る。必須欄を見出しにした本文を `$BODY` に書く。シェル展開で本文を渡さない（バッククォートや `$` が壊れる）

   `trap 'rm -f "$BODY"' EXIT` は、そのシェルに既にある EXIT trap を消して置き換わる。`trap -p EXIT` が空なら、その trap を置く。既にコマンドがあるなら、そのコマンドを残したまま `rm -f "$BODY"` を足した 1 本の trap にする。新しい trap だけで置き換えない。trap を置かないときは、成功・失敗・中止のどれでも、同じシェルを抜ける前に `rm -f "$BODY"` で消す
6. `TITLE` は型の接頭辞を含むタイトル、`LABEL` は手順 3 または 4 で決めた名前にする。コマンドの `--label` は `$LABEL` とし、`bug` のように型で固定した名前を書かない

   ```
   gh issue create --repo OWNER/REPO --title "$TITLE" --label "$LABEL" --body-file "$BODY"
   ```

   例: `[改修]` で既存が無いとき `TITLE='[改修] 一覧の絞り込みを保存できるようにする'`、`LABEL=improvement`。既存が `Improvement` なら `LABEL=Improvement`。`[作業]` なら正規名は `task`、`[アイデア]` なら `idea`、`[Bug]` なら `bug` で、いずれも既存の表記があればそちらを `LABEL` にする

次のときは中止する。ラベルを外して起票したり、別リポジトリのラベルで代用したり、`--label` を外して再実行したりしない。

- 作成先が決まらない
- ラベル一覧の取得に失敗した
- 大文字小文字を無視した完全一致が 2 件以上ある
- `gh label create` が失敗した
- `gh issue create` が失敗した

`gh issue create --label` は、作成先に無いラベルだと失敗する。

個人のフックや判定スクリプトの実行は前提にしない。
